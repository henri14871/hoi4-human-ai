# Technical notes

How `version.dll` works, and the reverse-engineering behind it. For install and usage, see the
[main README](../README.md).

## Engine map

Everything below was found by static analysis of `hoi4.exe` 1.19.4.1. The offsets are RVAs in that
build. The DLL does **not** hard-code them: it finds them at startup by byte signature and MSVC
RTTI, so small patches shouldn't break it. If anything fails to match, it logs the failure and
leaves the game vanilla.

| What | Where | How it was found |
|---|---|---|
| `g_humanAI` byte | `+0x33ddaa9` | Handler of the `human_ai` console command (`!flag`, prints "Human AI is now ON/OFF") |
| `IsAITag(gamestate, &tag)` | `+0x1f8460` | `is_ai` trigger (`CIsAITrigger`, vtable slot 22): `IsAITag(...) \|\| g_humanAI` |
| gamestate pointer | `+0x33dd6b0` | First argument to `IsAITag` |
| `CCountry` tag | `CCountry+0x8` | `IsAIControlled(country)` at `+0x747ab0` passes `&country->+8` |
| `CCountryAI::GetCountry` | `+0x2c02b0` | Called at the top of the module updates on `module->[+8]->vfunc1()` |
| AI modules | RTTI | `CAIModule` subclasses: `CAIForeignMinister`, `CAIInteriorMinister`, `CAIMilitaryMinister`, `CAIPoliticalMinister`, `CAIGeneral`, `CAIBaseGeneral`, `CAIVolunteerGeneral`, `CCryptologyAI` |
| Update slots | `CAIModule` vtable 11–17 | Profiler labels `Module.Update`, `.UpdateAIRoles`, `.HourlyUpdate`, `.DailyUpdate`, `.WeeklyUpdate`, `.MonthlyUpdate`, `.YearlyUpdate` |
| Theatre update | `+0x1145890` | Called by `CAIMilitaryMinister` Hourly (13) and Daily (14) updates; runs the air and naval sub-AIs |
| Air sub-AI | minister `+0x138` | `+0x135da00` air bases, `+0x13542f0` mission planning (reads `AI_FRACTION_OF_FIGHTERS_RESERVED_FOR_INTERCEPTION`), `+0x1146c10`/`+0x1146530` mission scoring |
| Naval sub-AI | minister `+0x5a0` | `+0x1afbd40` naval objectives (reads `AI_NAVAL_GOALS_UPDATE_FREQUENCY_DAYS`), `+0x1b5d10` gate in front of the rest of the naval block |

Confirmed in game (1.19.4.1): every module resolves through `owner = CCountryAI` to its country,
and human countries are told apart correctly (`ai_country=0`).

## Runtime

1. `proxy.cpp` forwards all 17 `version.dll` exports to System32 and starts an init thread, but
   only inside `hoi4.exe`. The launcher and `dowser.exe` load it too.
2. Turning on any area sets `g_humanAI` (the same switch as the `human_ai` console command), so
   the engine runs the AI for human countries.
3. Every update slot of every module class is redirected through `HaiThunk` (`asm.asm`), which
   preserves the register arguments and calls `HaiShouldRun`. For an AI country it always runs the
   original. For a human country it runs only if that module's area is handed to the AI.
4. Land, air and navy are split like this:
   - **land** = `CAIGeneral`/`CAIBaseGeneral` (fronts, armies, army groups).
   - **air** and **navy** live inside `CAIMilitaryMinister`, so that minister runs when any of the
     three is on.
   - Six call sites in its theatre update are patched to gate air and navy individually. A skipped
     naval gate returns `false`, which skips the whole naval block.
   - If that signature ever stops matching, air and navy just follow the minister.

Other `g_humanAI` readers (35 in total) mostly suppress player popups, such as focus-complete,
tech-unlock and template notices, while human AI is on.

## Settings window

`app/HumanAI.cs` builds `HumanAI.exe`, a Windows Forms app in C# 5 so it compiles with the
`csc.exe` that ships with Windows' .NET Framework 4.x. It never touches the game process:
- **Starting:** after hooking, the DLL launches it with `--pid <hoi4 pid>` and
  `SW_SHOWNOACTIVATE`. The window also overrides `ShowWithoutActivation`, so the game keeps focus.
  `launch_app=0` turns this off.
- **Closing:** it closes once that process exits. Started by hand with no game running, it says so
  and exits.
- **One copy only:** a named mutex stops a second copy.
- **Settings:** it edits `human_ai.ini`, which the DLL re-reads within a second, and it picks up
  hand edits too.
- **Status:** it reads `human_ai_status.ini`, which the DLL writes with
  `state=active|unsupported|stood_down`, `pid`, hook counts and `engine_flag`. The `pid` check
  ignores a stale file from an earlier session.
- **Layout:** it stays on top by default, for borderless fullscreen, and remembers its position
  under `[app]`.

## In-game panel (Workshop mod)

`workshop/` is the optional mod, generated by `tools/gen_panel.py`. It's plain HoI4 script:
- `interface/hai_panel.gui` has the layout.
- `common/scripted_guis/hai_panel.txt` has the buttons.
- `common/on_actions/hai_on_actions.txt` re-sends the campaign's choices when a save loads.

The buttons set global flags, which is how choices get saved per campaign, and run
`log = "HAI_CMD <area> <0|1>"`. The DLL tails `Documents\Paradox Interactive\Hearts of Iron
IV\logs\game.log` four times a second, and writes each command into `human_ai.ini`, so the settings
window mirrors it. It skips whatever is in the file at launch, and starts over when the game
truncates it. Opening the panel also re-sends its state, so the DLL always matches what the panel
shows.

Two details:
- **Everything is inlined.** HoI4 loads scripted GUIs before scripted effects, so the GUI can't
  call scripted effects.
- **The AI can't press the buttons.** The GUIs have `ai_enabled = { always = no }`, because with
  `human_ai` on the game treats the player as AI.

## AI packs (define registry)

`src/defines.cpp` rebuilds the game's define registry at runtime:
- **Lookup:** every define has a reader that loads its category table (`lea rdx, "NAI"`), then calls a
  typed reader with `lea r8, [value] ; lea rdx, "NAME"`.
- **Types:** the typed readers are classified by behaviour, not address. A `mulss` by `100000` or
  `32768` means fixed point (`int64 = round(v × scale)`), `movss [r12]` means float, and
  `mov [r12], ebx` means int32.
- **Coverage:** build 1.19.4.1 has 4,489 defines (947 `NAI`, 16 `NAITheatre`), of which 312 are arrays or strings.
- **Applying a pack:** only `NAI`/`NAITheatre` lines from `human_ai_packs\<pack>\common\defines\*.lua`
  are written, in file-name order. The originals are saved and restored when you switch packs. It
  happens once a game session exists, after the game has read its own defines.
- **Tested with Frontline AI 3.0:** 511 AI defines applied, 20 not in this game version, 69 gameplay
  defines ignored; its 16 AI arrays are applied in a running game when their lengths match.

**Arrays:** an array define is `{ float* data; int count; }` (read as `mov rax,[var] ; mulss
xmm,[rax+4]`). A pack array is written only if the game's array has the same length and its
current values really are floats, so int arrays are refused, not corrupted. Arrays can only be
checked in a running game; the self-test reports them as not applicable.

**Multiplayer-safe defines:** some `NAI` defines are also read by simulation code. For example,
`DEFAULT_SUPPLY_TRAIN_NEED_FACTOR` is read by `CGameState::MonthlyUpdate`, and changing it on one
PC desynced the supply cache. `tools/define_users.py` classifies every `NAI`/`NAITheatre` define by
who reads it:
- **Method:** it finds the functions that read each define's value, walks their callers up four
  levels to the classes that own them (RTTI), and labels each owner.
- **Labels:** AI classes (`…AI`, `CAI…`, ministers, generals) and display classes (`…Item`,
  `…View`, `…Window`, tooltips, portraits, the top bar) are safe. Anything else is "sim" (for
  example `COrdersGroup`, `CInGameIdler`, diplomatic actions, `CGameState`). No owner found counts
  as "unknown".
- **Use:** only "ai" defines go into `src/ai_only_defines.inc`, which is compiled into the DLL. In
  multiplayer and in `mp_test`, packs apply only those. Single-player applies everything.
- **Results on 1.19.4.1:** 551 ai, 181 sim, 231 unknown. Frontline AI keeps 309 of its 547 AI
  settings in multiplayer.

Regenerate it after a game update. It takes a few minutes:

```bash
py native/tools/define_users.py --inc native/src/ai_only_defines.inc
```

**Multiplayer test mode** (`mp_test=1`, single-player only): your country's AI runs as on a
client (no global `human_ai`, per-country gate, multiplayer-safe defines), while every command it
posts is dropped. Comparing `dump_checksum` / `compare_to_last_checksum` between a run with your
areas off and one with them on shows any side effect that would desync a real game. See the main
README for the steps.

**AI database folders** (`src/aidata.cpp`):
- **Finding the loaders:** the loading screen loads each AI folder with `lea rdx,"common/<folder>" ;
  call <string ctor> ; call <db wrapper> ; call <string dtor>`. Each wrapper stores the folder,
  calls `LoadFiles(db, path)`, then post-processes (`[rax+0x10]`) and links (`[rax+0x20]`).
- **The hook:** the `LoadFiles` call in the wrappers for `ai_strategy`, `ai_strategy_plans`,
  `ai_templates`, `ai_equipment` and `ai_areas` is redirected (via `HaiDbThunk`). It runs the game's
  own folder, then mounts the pack with the exported `PHYSFS_mount(pack, "hai_pack", 1)`, and loads
  `hai_pack/common/<folder>` into the same database before it's linked.
- **Install order:** these hooks go in first at startup, and only when the selected pack has one of
  those folders.
- **Prepare step** (`src/prepare.cpp`): before mounting, the pack's AI folders are copied to
  `<pack>\.hai\common\`. Each call to one of the pack's scripted triggers (`name = yes|no`) is
  replaced by the trigger's body (`AND = { … }`, or `NOT = { AND = { … } }`), repeated so triggers
  calling triggers expand too. `<pack>\.hai` is what gets mounted. The game's trigger database is
  never touched, so a pack can't redefine a vanilla trigger. Triggers with `$PARAMS$` are left as
  is. Tested with Frontline AI + AI Divisions + AI Designs: 91 triggers, 58 files, 245 calls
  expanded, all braces balanced.

The self-test parses a pack too. Set `HAI_TEST_PACK=<pack folder>` before running it.
On 1.19.4.1 it finds 4,489 defines, matching the game's own "4489 defines loaded".

## Config file

`human_ai.ini` sits in the game folder. The settings window and the in-game panel (through the DLL)
both write it, and the DLL re-reads it when it changes.

```ini
[human_ai]
enabled=1      ; 0 = mod idle, game vanilla
foreign=0      ; 1 = the AI runs it for you
interior=0
political=0
land=0
air=0
navy=0
volunteers=0
cryptology=0
launch_app=1   ; open HumanAI.exe when the game starts
ai_pack=       ; folder in human_ai_packs, empty = vanilla AI
mp_test=0      ; 1 = single-player stand-in for a multiplayer client (see README)

[app]          ; written by HumanAI.exe
keep_on_top=1
x=24
y=900
```

The DLL logs to `human_ai.log` in the game folder.

## Offline self-test

This maps `hoi4.exe` as an image (nothing runs) and does every lookup the real startup does,
without patching anything. Run it from the `native` folder after building, with your own game
path:

```bash
py -c "import ctypes;f=ctypes.WinDLL(r'build\version.dll').HaiSelfTest;f.argtypes=[ctypes.c_char_p]*2;print(f(rb'C:\Program Files (x86)\Steam\steamapps\common\Hearts of Iron IV\hoi4.exe',b'build'))"
```

`1` means pass. Details are in `build/human_ai.log`. Run it first after every game patch.

## Not verified yet

- **Exactly what each minister covers.** The area descriptions come from class names and the
  strings their code reaches.
- **How cleanly land, air and navy separate.** With only `air` or only `navy` on, the military
  minister still runs its other work for you: theatres, invasion planning, and two unlabelled calls
  (`+0x113fdd0`, `+0x113f680`). Naval invasions and transfers are planned by `CAIGeneral`. Air or
  naval orders issued from anywhere other than the six hooked sites are not gated.
- **Things outside the modules.** With `g_humanAI` on, the engine may also answer some prompts
  for you, such as event options and diplomatic replies.

## Analysis tools

`tools/` holds the Python scripts used to find all of this (`pip install pefile capstone`):
- `xref_string.py`, `xref_global.py`, `disasm.py`, `callees.py`
- `profiler_labels.py` lists profiler scope labels
- `reach.py` shows which labelled code a function or module reaches
- `owner.py` finds the RTTI class that owns a function, following chained unwind info
- `vtables.py` dumps vtables and shows which slots each class overrides

Set `HOI4_EXE` to point them at your game.
